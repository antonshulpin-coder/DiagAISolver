# DIAGNOSTIC_DESIGN.md — Архитектурный план v1.2: AI Diagnostic SOLVE

## 1. Цель

Превратить SOLVE из линейного сценария

```
проблема → AI-анализ → решение
```

в итеративное расследование:

```
проблема → гипотезы → проверка → результат проверки → новые гипотезы → решение
```

Диагностика — это осознанное движение к причине через проверяемые гипотезы. Каждая проверка даёт факт, который сужает пространство гипотез. Когда гипотеза подтверждается/закрывается пользователем — диагностика завершается переходом к решению.

---

## 2. Принципы (не нарушать существующее)

### 2.1. Обратная совместимость

- Существующий SOLVE (`solve.py`, `commands.py`) работает ровно как раньше.
- `NullProvider` продолжает возвращать `success=False` — диагностика работает в **полностью локальном режиме** (пользователь сам формулирует гипотезы и проверки).
- Существующие 351 тест не должны ломаться.
- Никакой миграции данных в `problems.json` — старые записи остаются валидными.

### 2.2. Граница Core / AI (из AI_DESIGN.md)

- AI — советник: возвращает структурированный результат, НЕ изменяет данные.
- Harness (Core) — хозяин данных: создаёт/смещает гипотезы, сохраняет, решает.
- AI не сохраняет ничего (stateless).
- API key не хранится нигде.

### 2.3. Минимум абстракций

Новые модельки — это **dataclasses из stdlib** или **обычные dict**. Никаких ABC/Protocol/фабрик сверх необходимого.

### 2.4. Всё тестируемо

Каждая новая функция покрыта тестами; существующие тесты не меняются (кроме случаев, когда это действительно необходимо — но по дизайну их менять не нужно).

## 3. Модель DiagnosticSession

Диагностическая сессия — это **контейнер** прогресса расследования одной проблемы. Она живёт **внутри записи Problem** (поле `diagnostic`), не отдельным файлом.

```python
# структура поля problem["diagnostic"] (dict | None)
{
    "active": true,                # идёт ли диагностика (см. 3.1)
    "started_at": "2026-08-27T...",# ISO 8601, когда началась диагностика
    "hypotheses": [ ... ],         # список Hypothesis (см. 4)
    "steps": [ ... ],              # список InvestigationStep (см. 5)
    "conclusion": "",              # финальный вывод (причина), заполняется при завершении
}
```

### 3.1. Поле `active`

`active: true` — диагностика открыта, пользователь может продолжить.

Когда диагностика завершается одним из способов:
- `resolve_problem()` вызывается с `cause` (значит причина найдена) → диагностика помечается завершённой.
- Пользователь явно завершает диагностику через CLI («завершить диагностику»).

`active` задумана как **производный признак** — она пересчитывается из наличия незакрытых гипотез / открытых шагов. Это предотвращает «забытые открытые сессии» и упрощает фиксацию.

**Решение:** `active` НЕ хранится, а вычисляется (`проблема в статусе investigating` И `есть незакрытые гипотезы` ИЛИ `есть непроверенные шаги`). Это устраняет риск рассинхронизации данных. Подробнее в разделе 6.

> Уточнение на этапе реализации: поле `diagnostic.started_at` хранится (для информации), но `active` вычисляется. Никакой отдельной миграции не нужно — отсутствие `diagnostic` = «диагностики не было».

## 4. Модель Hypothesis

```python
@dataclass
class Hypothesis:
    id: str                      # uuid4 hex, 8 символов (короткий, для CLI)
    text: str                    # формулировка гипотезы (что может быть причиной)
    status: str                  # "open" | "confirmed" | "rejected" | "tested"
    confidence: float = 0.0      # уверенность AI (0-1) или 1.0 если введена пользователем
    source: str = "ai"           # кто предложил: "ai" | "user" | "knowledge"
    created_at: str = ""         # ISO 8601
    last_tested_step_id: str | None = None  # какой шаг проверял её (ref на InvestigationStep)
```

### Status lifecycle гипотезы

```
open → tested (проверена, но не решена окончательно)
open → confirmed (пользователь подтвердил причину)
open → rejected (пользователь отверг)
```

- `confirmed` — гипотеза подтверждена как причина → диагностика может завершиться.
- `rejected` — гипотеза опровергнута → исключается из пространства.
- `tested` — была проверена шагом, но результат неоднозначен (шаг не подтвердил и не отверг её окончательно).

### Зачем отдельные поля

- `id` — для ссылок из InvestigationStep (`hypothesis_id`).
- `source` — откуда гипотеза (AI/пользователь/знания). Помогает понять доверие и фильтровать.
- `confidence` — AI честно говорит уверенность; пользовательские гипотезы получают `1.0`.
- `status` + `last_tested_step_id` — связывают гипотезу с проверкой (см. контекст для AI).

## 5. Модель Check / InvestigationStep

```python
@dataclass
class InvestigationStep:
    id: str                      # uuid4 hex, 8 символов
    hypothesis_id: str | None    # какая гипотеза проверяется (None = свободная проверка)
    description: str             # что проверить (инструкция)
    status: str                  # "pending" | "done"
    outcome: str = ""            # что выяснилось (факт после проверки)
    result: str = ""             # "confirmed" | "rejected" | "unknown" — влияет на гипотезу
    created_at: str = ""         # ISO 8601
    completed_at: str = ""       # ISO 8601, когда завершён
```

### Status lifecycle шага

```
pending → done
```

- Шаг создаётся (`pending`), пока пользователь его не выполнил.
- Когда пользователь отмечает «проверил» и вводит результат → `done`, заполняется `outcome` и `result`.
- `result`: `confirmed` (гипотеза подтвердилась), `rejected` (опроверглась), `unknown` (неоднозначно).

### Как результат шага влияет на гипотезу

| `step.result` | Эффект на связанную гипотезу |
|---------------|------------------------------|
| `confirmed` | Гипотеза → `confirmed` (причина найдена) |
| `rejected` | Гипотеза → `rejected` (исключается) |
| `unknown` | Гипотеза → `tested` (остаётся, но помечена проверенной) |
| нет `hypothesis_id` | гипотеза не меняется (свободная проверка) |

Это ядро «итеративного расследования»: каждый шаг — атомарный факт, двигающий пространство гипотез.

## 6. Жизненный цикл диагностики

### 6.1. Когда диагностика доступна

Диагностика — это **расширение** статуса `investigating`. Проблема в `investigating` может иметь диагностическую сессию. Проблема в других статусах (`new`, `solving`, `solved`, `failed`, `archived`) — диагностика не активна (поле `diagnostic` может существовать как история, но не редактируется).

### 6.2. Поток

```
create_problem → status=new
    ↓
start_investigation() → status=investigating
    ↓
[диагностика]  инициализация diagnostic = {started_at, hypotheses:[], steps:[]}
    ↓
цикл:
    AI предлагает гипотезы (analyze_hypotheses)
    пользователь добавляет/отклоняет гипотезы
    AI предлагает следующий шаг проверки (suggest_check)
    пользователь выполняет проверку, вводит результат
    результат обновляет гипотезу (confirm/reject/tested)
    ↓ повтор, пока:
      · гипотеза не подтверждена → причина найдена → к решению
      · пользователь не решил «завершить» → к решению
      · достигнут лимит итераций → предупреждение, предложить решение
    ↓
start_solving() → status=solving
    ↓
resolve_problem() → status=solved/failed  (diagnostic.conclusion = cause)
```

### 6.3. Переход к решению

Диагностика заканчивается **до** `start_solving()`. Причина, найденная диагностикой, передаётся в решение.

- Пользователь завершает диагностику → `start_solving()`, затем `_do_solve()` (существующий код).
- `resolve_problem(cause=...)` уже записывает `cause`. `diagnostic.conclusion` дублирует причину для истории расследования (см. раздел 7).

## 7. Какие данные сохраняются в problems.json

В поле `problem["diagnostic"]` сохраняется **только факты и состояние**:

| Сохраняется | Почему |
|-------------|--------|
| `started_at` | Когда началась диагностика (для отображения/статистики) |
| `hypotheses[]` (id, text, status, confidence, source, created_at, last_tested_step_id) | Нужны для возобновления и для контекста AI |
| `steps[]` (id, hypothesis_id, description, status, outcome, result, created_at, completed_at) | Полный журнал проверок — воспроизводимое расследование |
| `conclusion` (причина) | Краткий финальный вывод |

`diagnostic.active` **НЕ хранится** — вычисляется (раздел 3.1).

---

## 8. Какие данные НЕ сохраняются

| НЕ сохраняется | Почему |
|----------------|--------|
| Полный текст AI-ответа (content) | Это советник, не факт. Мы сохраняем только структурированную производную (гипотезу, шаг) |
| `AIResponse` целиком | Формат провайдера, не модель данных |
| Исходные промпты | Раздувают JSON, не нужны для возобновления |
| API key / любые секреты | Данные пользователя отделены от секретов |
| Временные AI-confidence ниже порога | Мусор, раздувает файл |
| `steps` с пустым `outcome` (незавершённые) — НЕ удаляются, хранятся как `pending` | Журнал должен быть полным для истории |

## 10. Какие новые AIProvider methods действительно нужны

Проектируем **минимально необходимое** — не больше двух новых методов, и оба опциональны (NullProvider возвращает `success=False`).

### 10.1. `suggest_hypotheses(problem, search_results, diagnostic_context) -> AIResponse`

- Когда: при открытии диагностики и после каждой проверки.
- Вход: проблема + найденный опыт + **компактный контекст диагностики** (что уже проверяли).
- Выход: AIResponse, где `suggestions` = список строк-гипотез. `content` = пояснение.
- Позволяет AI предлагать новые гипотезы, **не повторяя отклонённые** (контекст предшествующих проверок).

### 10.2. `suggest_next_check(problem, hypotheses, steps, diagnostic_context) -> AIResponse`

- Когда: когда есть хотя бы одна открытая гипотеза, требующая проверки.
- Вход: проблема + открытые гипотезы + журнал проверок.
- Выход: AIResponse, где `content` = описание одного шага проверки (что проверить и как). `suggestions` = альтернативные шаги.
- Позволяет AI подсказать, **что проверить следующим**, исключая уже сделанные шаги (контекст в `diagnostic_context`).

### 10.3. Почему только 2 новых метода

- Существующих 5 методов покрывают линейный SOLVE (анализ, план, результат, форматирование).
- Диагностика добавляет ровно 2 новых операции: «предложить гипотезы» и «предложить следующий шаг». Это ядро итерации.
- **Не добавляем:** `analyze_check_result` (результат — простые факты confirmed/rejected/unknown, их вводит пользователь, AI не нужен); `summarize` (это делает Core в `conclusion`).

### 10.4. Контракт в provider.py

```python
class AIProvider:
    def suggest_hypotheses(self, problem, search_results, diagnostic_context) -> AIResponse:
        raise NotImplementedError   # NullProvider → success=False

    def suggest_next_check(self, problem, hypotheses, steps, diagnostic_context) -> AIResponse:
        raise NotImplementedError
```

`NullProvider` и `FakeProvider` получают эти методы. `OpenAIProvider` — реализует через `_chat` с json-контекстом.

## 11. Как AI получает контекст предыдущих проверок

### 11.1. Функция `get_diagnostic_context()`

```python
def get_diagnostic_context(problem, max_steps=5):
    d = problem.get("diagnostic") or {}
    return {
        "open_hypotheses": [_compact_hypothesis(h) for h in d.get("hypotheses", [])
                            if h["status"] in ("open", "tested")][:MAX_OPEN_HYPOTHESES],
        "rejected_hypotheses": [_compact_hypothesis(h) for h in d.get("hypotheses", [])
                                if h["status"] == "rejected"][:MAX_REJECTED_HYPOTHESES],
        "recent_steps": [_compact_step(s) for s in d.get("steps", [])
                         if s["status"] == "done"][-max_steps:],
        "conclusion": d.get("conclusion", ""),
    }
```

- **Открытые гипотезы** — AI знает, что ещё не проверено.
- **Отклонённые гипотезы** — AI не предлагает их снова.
- **Последние шаги** — AI знает, что уже проверяли, и не повторяет.
- **Вывод** — если частично есть.

### 11.2. Компактные представления (аналог `_compact_knowledge`)

```python
def _compact_hypothesis(h):
    return {"text": h["text"], "status": h["status"], "source": h["source"]}

def _compact_step(s):
    return {"description": s["description"], "result": s["result"]}
```

## 12. Как ограничить размер контекста

### 12.1. Лимиты (в context builder диагностики)

| Параметр | Значение | Почему |
|----------|----------|--------|
| `MAX_OPEN_HYPOTHESES` | 5 | Показываем AI только самые важные открытые |
| `MAX_REJECTED_HYPOTHESES` | 5 | Достаточно для «не повторять» |
| `MAX_RECENT_STEPS` | 5 | Последних проверок достаточно |
| Длина `hypothesis.text` | 200 символов | Гипотеза — короткая фраза |
| Длина `step.description` | 300 символов | Инструкция проверки краткая |
| Длина `outcome` | 300 символов | Факт после проверки |

### 12.2. Стратегия

- Контекст = компактный срез, **не весь журнал**.
- Любой длинный текст обрезается.
- Не передаём ID, created_at, completed_at (не нужны AI).
- Не передаём полный `problems.json`.

## 13. Как избежать бесконечного цикла диагностики

### 13.1. Жёсткий лимит итераций

`MAX_HYPOTHESES_PER_SESSION = 10` — максимум гипотез в сессии.
`MAX_STEPS_PER_SESSION = 20` — максимум шагов проверки в сессии.

При достижении лимита:
- CLI показывает предупреждение: «Достигнут лимит диагностики (10 гипотез / 20 проверок). Рекомендуется перейти к решению».
- `add_hypothesis` / `suggest_check` / `add_check` бросают `SolveError` с явным сообщением («Лимит диагностики превышен»).
- Пользователь может завершить диагностику и перейти к решению (не блокируется).

### 13.2. Критерий завершения

- Гипотеза подтверждена (`confirmed`) → причина найдена → диагностика завершается.
- Все открытые гипотезы отклонены или `tested` без подтверждения → предложить завершение.
- Пользователь сам может завершить в любой момент.

### 13.3. Не блокируем SOLVE

Лимиты защищают от бесконечного цикла, но **не** мешают обычному SOLVE. Пользователь всегда может выйти из диагностики в меню, а из меню — продолжить решение без диагностики.

## 14. Что происходит при недоступном AI

### 14.1. Принцип fail-safe (из AI_DESIGN.md)

AI недоступен → диагностика работает в **локальном режиме**:

| Сценарий | Поведение |
|----------|-----------|
| AI отключён (enabled=false) | NullProvider → `suggest_hypotheses` вернёт `success=False` → CLI предложит пользователю ввести гипотезу вручную |
| Нет API key | То же (NullProvider/OpenAIProvider без key → success=False) |
| Сбой сети/API | `_safe_ai_call` ловит исключение → `success=False` → локальный режим |
| Таймаут | `success=False` → локальный режим |

### 14.2. Локальный режим

- Пользователь вводит гипотезу вручную (`add_hypothesis(text=..., source="user")`).
- Пользователь сам придумывает и формулирует шаг проверки (`add_check`).
- Результат проверки вводит пользователь (`complete_check`).
- `convert_to_knowledge`, `resolve_problem` и весь SOLVE работают без изменений.

## 15. Что происходит при ошибочном AI-ответе

### 15.1. Уровень провайдера (уже реализован)

- `OpenAIProvider` возвращает `success=False` + `error` при: 401/403/429/5xx, таймаут, сетевой ошибке, malformed JSON, refusal, null content (всё покрыто в v1.1.1).
- `_safe_ai_call` оборачивает любой вызов — исключения не вылетают наружу.

### 15.2. Уровень диагностики

- `ai_suggest_hypotheses` / `ai_suggest_next_check` используют `_safe_ai_call` → всегда возвращают `AIResponse` (success может быть False).
- Если `success=False` → CLI показывает «AI недоступен», предлагает ввод вручную (раздел 14).
- Если `success=True`, но `suggestions` пустые / мусор → игнорируем AI-вклад, работаем в локальном режиме (не крашим).

### 15.3. Валидация AI-предложений

- Каждая гипотеза — строка; пустые строки отбрасываются.
- Дубли (по нормализованному text) отбрасываются (см. `add_hypotheses` дедупликация).
- Гипотезы, совпадающие с уже `rejected`, отбрасываются.
- `suggest_next_check` — берём `content` как основной шаг; если пусто — отбрасываем.

## 16. Как пользователь может выйти и продолжить позже

### 16.1. Все данные — в problems.json

Диагностика (гипотезы, шаги) сохраняется в `problem["diagnostic"]` при каждой мутации (`add_hypothesis`, `add_check`, `complete_check`). Поэтому состояние полностью восстанавливается.

### 16.2. Выход в меню

- Пункт «Сохранить и выйти» в любом подменю диагностики → возврат в главное меню SOLVE.
- Проблема остаётся в `investigating` с `diagnostic`, содержащим прогресс.

### 16.3. Продолжение позже

- `_continue_existing_problem()` показывает площадку: активные проблемы (включая `investigating`).
- Выбор investigating → `_investigate_problem()` → если есть `diagnostic` → показываем «Продолжить диагностику» и подхватываем открытые гипотезы/шаги.
- Ни одна гипотеза/шаг не теряется.

## 17. Как завершённая диагностика превращается в Knowledge Record

### 17.1. Цепочка

```
диагностика завершена (conclusion = причина)
    ↓
start_solving() → status=solving
    ↓
resolve_problem(cause=conclusion, solution=..., helped=...) → solved/failed
    ↓
convert_to_knowledge() → Knowledge Record (type="solution")
```

### 17.2. Включение расследования в текст знаний

`_build_knowledge_text()` (существующая функция) расширяется необязательной секцией «**Расследование**»:

```
Расследование:
- Гипотеза: "сломан venv" → Проверено: активировал venv → подтверждена
- Гипотеза: "нет пакета" → Проверено: pip install → отклонена
```

Это делает Knowledge Record ценным — сохраняется не только решение, но и **ход расследования** (что исключено, что подтверждено).

- Если `problem["diagnostic"]` нет (обычный SOLVE) → секция не добавляется, текст ровно как раньше (обратная совместимость).
- Текст собирается из `hypotheses` + `steps` с ограничением длины (последние N элементов).

### 17.3. `related_record_id` уже устанавливается `convert_to_knowledge` — без изменений.

## 18. Интеграция в CLI (commands.py)

### 18.1. Новый поток `_investigate_problem` (расширение)

Существующий `_investigate_problem` сохраняется как fallback/линейный путь. Добавляется опция «**Диагностика**»:

```
_handle_existing_problem: investigating
    ├── 1. Продолжить диагностику (если есть diagnostic)
    ├── 2. Начать диагностику (новая)
    ├── 3. Линейное расследование (как раньше)
    ├── 4. Перейти к решению
    └── 0. Назад
```

### 18.2. Цикл диагностики в CLI

```
show диагностика (открытые гипотезы, шаги, результат)
1. AI предложить гипотезы     (suggest_hypotheses, если AI доступен)
2. Добавить гипотезу вручную
3. Предложить следующий шаг   (suggest_next_check, если AI доступен)
4. Добавить шаг проверки вручную
5. Отметить шаг выполненным   (ввод outcome + result)
6. Подтвердить причину        (завершить диагностику → start_solving)
0. Сохранить и выйти
```

- Все AI-вызовы опциональны и обёрнуты.
- Пользователь возвращается в цикл после каждого действия.

### 18.3. Связь причины

При «Подтвердить причину» CLI вызывает `finish_diagnostic(problem_id, conclusion)` затем `start_solving()`, затем `_do_solve()` (существующий). Пользователю не нужно вводить причину повторно в `_do_solve` — она предзаполнена из `conclusion`.

## 22. Риски и спорные решения

### Риск: Раздувание problems.json журналом расследования
Длинные расследования могут раздуть файл. Решение: лимиты (20 шагов), `clean_diagnostic()` для удаления завершённой диагностики, компактные тексты (обрезание).

### Спорное: Хранить диагностику в поле Problem, а не отдельным файлом
**За:** одна запись = одно расследование, проще бэкап, атомарность с проблемой.
**Против:** большой problem-object. **Решение:** хранить в поле; лимиты защищают объём.

### Спорное: `active` вычисляется, а не хранится
**За:** нет рассинхронизации.
**Против:** чуть дороже вычислить. **Решение:** вычислять — проекция простая и дешёвая.

### Спорное: 2 новых AI-метода vs 1 универсальный
**За:** разделение «предложить гипотезы» и «предложить шаг» — разные вопросы, разные ответы, лучше для контекста и тестирования.
**Против:** больше кода. **Решение:** 2 метода, каждый минимальный.

### Риск: Регрессия существующего `_investigate_problem`
Решение: линейный путь полностью сохранён; диагностика добавляется как отдельная опция, не заменяет существующий поток.
